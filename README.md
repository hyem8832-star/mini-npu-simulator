# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 3×3 ~ 25×25 패턴이 Cross(십자가)인지 X인지 판별하는 Python 콘솔 앱입니다.

## 실행 방법

```
python main.py
```

- Python 3.8+ / 표준 라이브러리만 사용 (NumPy 등 없음)
- `1` 선택: 3×3 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력 → 점수·시간·판정 출력
- `2` 선택: 같은 폴더의 `data.json`을 읽어 일괄 판정 + PASS/FAIL + 성능 표 + 요약 출력
- `data.json`에는 5×5, 13×13, 25×25 필터/패턴과 **의도적 오류 케이스(`size_5_3`, 크기 불일치)** 1개가 들어 있습니다.

## 구현 요약

- **라벨 정규화**: `normalize_label()`이 `+`/`cross` → `Cross`, `x` → `X`로 통일. 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준.
- **MAC**: 이중 for문으로 `pattern[i][j] * filter[i][j]`를 누적 (`mac()`).
- **동점 정책**: `abs(a - b) < 1e-9`이면 `UNDECIDED`. UNDECIDED는 expected와 다르므로 FAIL.
- **입력 검증**: 모드 1은 줄당 개수/숫자 파싱 오류 시 안내 문구 후 재입력. 모드 2는 스키마·크기 오류를 케이스 단위 FAIL로 처리해 프로그램이 중단되지 않음.
- **보너스(패턴 생성기)**: `make_cross(n)`, `make_x(n)`로 N×N 패턴 생성, 성능 분석에 재사용.

## 결과 리포트

### 실패 원인 분석
실행 결과: 총 7개 / 통과 6개 / 실패 1개. 실패는 `size_5_3` 하나이며, 이는 **로직 문제가 아니라 의도적으로 넣은 데이터 문제**입니다.
`size_5_3`은 키가 `size_5`라 5×5 필터를 선택하지만 `input`은 3×3이라 크기 검증에서 걸려, MAC을 수행하지 않고 "크기 불일치" 사유와 함께 FAIL 처리됩니다.
나머지 6개는 모두 PASS인데, 그 이유는 다음과 같습니다.
첫째, 라벨 정규화 덕분에 data.json의 `+`/`x`(expected)와 `cross`/`x`(필터 키)가 표준 라벨 `Cross`/`X`로 맞춰져 문자열 불일치로 인한 오판이 없습니다.
둘째, 필터와 같은 모양의 패턴은 점수가 크게 갈립니다(예: 5×5에서 9 vs 1, 25×25에서 49 vs 1). 점수 차가 1e-9보다 훨씬 크므로 UNDECIDED가 나오지 않습니다.
셋째, 값이 0/1 정수라 부동소수점 오차가 거의 생기지 않지만, 소수 값이 들어오면 `0.9`와 `0.8999999999999999`처럼 사실상 같은 값이 다르게 비교될 수 있어 `==` 대신 epsilon 비교를 사용합니다.
실패가 생기면 (1) 데이터/스키마(라벨, 키, 크기), (2) 로직(필터 선택, 연산), (3) 수치 비교(동점/오차) 순으로 원인을 분리해 진단합니다.

### 시간 복잡도 분석
MAC은 N×N 칸을 한 번씩 곱하고 더하므로 연산 횟수가 N²이고, 시간 복잡도는 **O(N²)** 입니다. 3×3은 9회, 25×25는 625회로 약 69배 늘어납니다.
측정 결과(10회 평균, 실행 환경에 따라 달라짐)는 다음과 같습니다.

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|------|--------------|---------------|
| 3×3 | 0.0036 | 9 |
| 5×5 | 0.0072 | 25 |
| 13×13 | 0.0590 | 169 |
| 25×25 | 0.1053 | 625 |

크기가 커질수록 시간이 증가하는 경향은 N²과 일치합니다. 다만 시간 증가폭이 연산 횟수 증가폭보다 작게 나오는 구간(예: 13→25는 연산 3.7배, 시간 약 1.8배)이 있는데,
이는 N이 작을 때 함수 호출·타이머 같은 고정 오버헤드와 측정 잡음(OS 스케줄링 등)이 큰 비중을 차지하기 때문입니다.
실제 NPU는 이 N²번의 곱셈을 병렬로 처리해 시간을 줄이는 하드웨어입니다.
